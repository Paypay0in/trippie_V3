# Trippie APP 功能紀錄

**這份文件是 Trippie 產品決策的正典來源（canonical source of truth）。**

適用範圍：已核准的產品原則、長期方向、跨票有效的工程約束。
不屬於這裡的：單張票的實作細節、當日進度、聊天記錄。那些留在 `memory/YYYY-MM-DD.md`。

原則一旦寫進這裡，後續所有開發都應視為既定前提，除非 Founder 另開票修改。

---

## 1. 個人化：Trippie 的長期護城河

**核准日期：2026-09-16｜決策者：Founder**

Trippie 應該隨著使用者旅行次數增加而越來越懂他。

長期護城河**不是**「會用 AI 生行程」——那件事誰都做得到。真正的護城河是：

```
Personal Travel Taste
+ Trip Context
+ Companion / Group Context
+ Current Budget Context
→ 越來越個人化的旅行建議
```

使用者在 Trippie 裡規劃、修改、執行、記錄的每一趟旅程，都應該讓下一趟規劃變得更好。

---

## 2. Travel Taste：從行為學，不是從問卷學

**行為是主要的長期學習訊號。** 不要依賴明確的偏好問卷——人填問卷時說的和實際旅行時做的經常不同。

應逐步從以下行為學習偏好：

- 收藏了哪些地點
- 接受了哪些 AI 建議
- 拒絕／略過了哪些 AI 建議
- 行程項目留下來的 vs 被刪掉的
- 項目被搬到哪一天、哪個時段
- 時間與時長的調整
- 偏好的每日行程密度
- 偏好的出發時間
- 交通方式選擇
- 住宿偏好
- 飲食／活動／購物傾向
- 與特定同行者一起時的行為差異

---

## 3. Budget Taste：學「怎麼花」，不是學「花多少」

Trippie 最終應該學會使用者旅行時偏好如何花錢：

- 價格敏感度
- 願不願意為「方便」付錢
- 願不願意為「獨特體驗」付錢
- 住宿／餐飲／交通／活動各自的花費傾向
- 購物傾向
- 通常可接受的每日花費
- 在精省／實惠／舒適／高端之間的傾向

### 絕對禁止：從單一選擇貼上永久標籤

選了一次最便宜的滑雪方案，**不代表**「這個人是精省型旅客」。

**偏好是有脈絡的。** 同一個人在下列情境會表現得完全不同：

- 獨旅 vs 有同行者
- 醫美行程 vs 一般觀光
- 蜜月 vs 背包旅行
- 日本 vs 東南亞
- 短程 vs 長程

因此未來的個人化必須把脈絡一起納入，不能只看歷史平均。

## 4. 工程註記：先保存事件，日後再推導偏好

> **preserve learning-event history now; derive preference models later.**

現階段**不要**急著建複雜的 ML。優先事項是**保存足夠豐富的行為歷史與出處（provenance）**，讓偏好模型日後可以被推導出來——資料沒存下來的那一刻就永遠回不去了，模型隨時可以重訓。

### 原始事件（raw events）

```
AI_PLAN_OPTIONS_SHOWN
AI_PLAN_OPTION_SELECTED
AI_PLAN_OPTION_DISMISSED
AI_PLAN_ADDED_TO_ITINERARY
ITINERARY_ITEM_EDITED
ITINERARY_ITEM_MOVED
ITINERARY_ITEM_DELETED
ACTUAL_EXPENSE_LINKED
```

每筆在相關時應保存：userId、tripId、requestId、optionId、**當時一起顯示的其他選項**、選項特徵、預估預算區間、幣別、目的地、同行者脈絡、產生的行程項目 id、時間戳。

### 訊號強度

**曝光不是偏好。** 螢幕上的每個選項都被「顯示」過，所以顯示本身不帶任何資訊。

強訊號依序是：**實際花錢 > 保留下來 > 編輯調整 > 選擇（相對於被放棄的選項）> 明確略過**。

這也是為什麼「被選掉的那些選項」必須跟著選擇一起存——只存 optionId 的話，事後無從得知這個選擇是在什麼之中做出的。

### 原始事件與衍生偏好必須分開存放

事件表只存發生過的事實，不存任何衍生標籤或偏好分數。偏好模型日後另建，可以重算、可以推翻；事件不行。

## 5. 活動規劃：推薦單位是「方案」，不是「地點」

使用者說「我想滑雪」時，Trippie **不應該**像搜尋引擎一樣傾倒場館清單與待辦事項。

### 核准的流程

```
使用者意圖
→ 研究（爬文）
→ 理解當前這趟旅程
→ 產出 2–3 個可執行的方案
→ 比較天數 / 交通 / 預算 / 取捨
→ 依個人化排序
→ 使用者選擇
→ 加入行程提案
→ 之後才談準備 / 預約 / 真人協助
```

**推薦單位應逐漸變成 PLAN，而不只是 PLACE。** 地點只是方案的一個組成部分。

一個方案要回答：做什麼、在哪、為什麼適合這趟、建議幾天、大致時段安排、交通與後勤影響、可支持時的預算區間、需要準備什麼、取捨是什麼、如何嵌入現有行程。

### 數量：品質優先

資料只支持一到兩個好方案時就給一到兩個。**不要為了湊三個而產生三張幾乎一樣的卡。**

方案之間要有實質差異：最省事 / 最適合這趟 / 完整體驗 / 較省錢 / 舒適便利 / 過夜。

### 準備事項排在選擇之後

證照、翻譯、保險、租借規定這些，在使用者還沒決定要做什麼之前就全部攤開，只會讓人直接滑過去。準備事項應該是**選定方案後、針對那個方案**才出現。

## 6. 事實歸屬：哪一層可以宣稱什麼

這是硬性約束，適用於所有 AI 功能，不限於活動規劃。

| 事實 | 擁有者 | 說明 |
| --- | --- | --- |
| 地點身分、座標、地址、官方連結 | **Places** | 模型不得產出地點識別或網址 |
| 交通時間 | **Routes** | 模型不得自行估算 |
| 開放期間、價格、是否需預約 | **grounded search** | 只能來自實際查到並可引用的頁面 |
| 綜合、取捨、方案差異化、時段編排 | **模型** | 僅此而已 |

**沒有查證過的價格 → 顯示「價格需確認」**，不得顯示數字。模型記憶中的價格與查證過的價格在畫面上長得一模一樣，而使用者會照著它編預算。這條必須在伺服器端強制，不能靠提示詞自律。

### 價格來源階層（Founder 核准，2026-09-16）

由可信度高到低，取第一個有值的：

1. **grounded search 查到的方案總花費** → 顯示區間，註記「整個方案的估計花費」
2. **地圖服務的場館價位**（Places `priceRange`／`priceLevel`）→ 只是**單一場館**的價位，必須明確註記「不含交通與其他花費」
3. 兩者皆無 → **「價格需確認」**

第 2 層存在的理由：grounded search 的配額經常耗盡，而地圖服務的價位跟地址、座標同一個來源，是真實資料而非模型記憶。但它涵蓋的範圍窄得多，所以**沒有那句註記就不准顯示**——`JPY 1,000–2,000` 會被讀成一整天的花費。

**模型記憶中的價格永遠不得進入事實價格層。**

### 數字要從實際內容推導，不要採信模型宣稱（Founder 核准，2026-09-16）

方案天數（`durationDays`）由方案自己的行程項目算出（`max(dayOffset) + 1`），不採用模型回傳的數字。

起因：在一趟 10 天的旅程裡詢問，模型三個方案全回「10 天」——那是旅程長度，不是方案長度，使唯一能區分方案的欄位變成雜訊。

通則：**畫面上顯示的數字，必須等於實際會被寫進行程的內容。** 項目才是真正會被插入的東西，所以由它決定天數。同樣的道理適用於任何可以從正典資料算出來的數字。

同理：查不到就說查不到。**不存在「憑印象的降級方案」**——沒有人能不查資料就說出哪個雪場適合初學者。

## 7. 同行者與群體脈絡（保留架構，現在不實作）

個人偏好不夠。Trippie 最終應該學會**關係層級**的模式。

Ann × Gina 一起旅行的偏好，可能完全不同於 Ann × 另一位同行者。

未來的規劃應該能結合個人偏好與群體歷史，用來：找出雙方都能接受的行程、指出衝突、提出折衷、必要時建議分頭行動。

**現在不要建這層 ML。** 但資料架構要保留這個可能性——事件中的同行者脈絡現在就要存。

## 8. 服務的經濟模型（Founder 核准，2026-09-19）

### 用錢，不用積分

協助需求以**金錢**成交。不發行積分作為交易媒介，也不承諾任何形式的點數兌現。

理由不只是法規，法規只是最後一層：

**旅行是極低頻的。** 一年出國一到兩次，一趟用到協助一到三次。貨幣要流通才有意義，
一年賺一次、一年花一次的東西不是貨幣，是折價券。

**服務是異質的。** 打一通電話訂位與陪同兩小時跑醫院差一個數量級，都可能落在
`on_site`。異質性高就無法標準化定價，「X 點換一次協助」這種菜單描述的是一個
Trippie 沒有在賣的東西。

**幫手是稀缺的一方。** 願意幫陌生旅客跑腿的在地人難找，旅客不難找。稀缺的一方
必須賺得到錢，不能用不能兌現的點數打發。

**承諾未來可兌現的積分是不可逆的。** 使用者一旦抱著「之後能換錢」的預期在累積，
平台實質上已經發行了尚未兌付的債權——觸發點是承諾，不是兌付日。這與第 6 節
「沒有查證過的價格就寫『價格需確認』」是同一條原則：**不做背不起的宣稱**。

積分若要存在，只能用於**獎勵社群貢獻**（遊記、經驗分享），且**明確永不兌現**，
與勞務報酬完全不互通。

### 目標形態：italki 式的押款市集（Founder 核准，2026-09-19）

長期形態已定：幫手自己開價、旅客付款進平台、平台押款、確認後放款、
逾時自動確認、平台抽成。這是成熟結構，不重新發明。

**但 v1 不做押款。** 分兩階段：

| 階段 | 內容 | 前提 |
|---|---|---|
| v1 | 媒合、雙向出價、完成確認、檢舉 | 無 |
| v2 | 押款、放款、抽成 | 法規諮詢、金流商、退款與稅務流程 |

這個切法的關鍵是：**確認與檢舉的設計在 v2 完全不用改**，押款是接在後面的一層。
先跑流程、累積真實客單價與成交率，費率才有根據可訂——單筆 NT$500–3,000 的
1% 是 5 到 30 元，低於金流手續費本身，**在知道真實客單價之前訂費率只是猜**。

**v1 期間 Trippie 不經手金流、不收取任何交易手續費。**

#### 與 italki 不同、不可照抄的四點

1. **履約證據**：italki 的課發生在平台上，平台自己有紀錄。Trippie 的服務發生在
   平台之外，爭議時平台手上沒有東西。**沒有證據的自動確認等於把疑義一律判給幫手**
   ——這是 v1 限定遠端服務的主要理由之一（見下節）。
2. **頻率與關係**：italki 的學生跟同一位老師上幾十堂課，聲譽有時間長出來。
   Trippie 是一年一次、對象是陌生人、不會再見——一次性賽局的作弊誘因高得多。
3. **押款就是持有他人資金**：這是 `電子支付機構管理條例` 的線。v2 動工前必須先取得
   正式法規意見，不可邊做邊問。
4. **最壞情況差一個量級**：italki 最糟是一堂爛課；Trippie 最糟是人身安全事故。
   檢舉機制在這裡不只是品質管理，是安全機制。

### v1 只做遠端服務：不含人身接觸（Founder 核准，2026-09-19）

v1 **只開放不需要見面的協助**：代打電話、訂位、文件與線上翻譯、查詢與諮詢。
**排除任何需要與旅客見面或同行的服務**——現場陪同、接送、帶路。

這一條同時解決三件事，不只是安全：

- **安全**：陌生人與旅客在異國單獨見面的最壞情況，在 v1 不存在
- **履約證據**：遠端服務自己會留下痕跡。訂位有編號、翻譯有交付物、詢問有結果可回報。
  上一節說「平台手上沒有證據」的問題，遠端反而有解，三天自動確認的風險跟著降低
- **同質性**：訂位、翻譯、詢問彼此的價差，遠小於它們與「陪同兩小時」的價差。
  價格統計因此才有意義（呼應本節的分組要求）

附帶好處：遠端服務**可以在出發前發生**，行前需求比旅程中多，稍微緩解低頻問題。

**實作上要關掉的**：`ServiceCategory` 的 `on_site`、`AssistanceNeed` 的 `on_site`。
型別保留（那是真實存在的未來概念），在**單一處**設定 v1 可用清單來擋，
不要把判斷散落各處。`other` 屬模糊地帶，需要額外把關。

**誠實的代價**：最有價值的協助——陪同就醫、陪同辦手續——正是被排除的那些。
v1 放棄的是真實需求，不是邊角。

**這是政策邊界，不是強制力。** 雙方在平台上談好之後線下見面，Trippie 擋不住。
能做的是：不提供促成見面的功能、明確說明平台不涵蓋、出事時的責任界線寫清楚。
**不要假裝這條規則能被執行。**

### 雙向出價

需求方填寫期望金額，幫手可以出價。幫手的報價是比單方填價更準的市場訊號。

### 價格參考：標籤必須反映資料的可信度

需求金額欄位旁顯示同類服務的價格參考。**這行字怎麼寫，取決於資料是怎麼來的：**

| 資料來源 | 可以叫它 |
|---|---|
| 使用者填寫的期望金額 | 開價 |
| 雙邊確認且金額一致 | 成交價 |
| 單邊確認 | 降權或排除，不可稱成交價 |
| 金額不一致（爭議） | 整筆排除 |
| 被檢舉 | 整筆排除 |

**不准**先寫「成交價」再打算之後補資料。標籤跟著資料走。

**「類似的服務」要分組**：至少依類別 × 時長級距 × 城市。把訂位電話和整日陪同
平均起來會得到一個對誰都不對的數字。

**樣本不足就明說沒有**，不要塞估計值（延續第 6 節）。建議門檻 5 筆。

**顯示區間優先於單一平均**（例如「多數落在 1,200–2,500」）。平均值會讓價格
向它收斂，壓縮高品質幫手的定價空間；區間留得下差異。

### 完成確認：雙邊按下

交易完成需要**雙方各自確認**，並各自填寫最終金額。

已知破口：**沒有人有動機按第二下。** 旅客付完錢、事情辦完，人就走了；
幫手為了收錢會確認，旅客不會。若不處理，多數交易會停在單邊確認，
價格資料永遠湊不到樣本。

**解法（Founder 核准，2026-09-19，採 italki 作法）：三天自動確認。**
幫手回報完成後，旅客有 **3 天**確認或提出異議；逾時視為已完成。

這正是「沒有人按第二下」的標準解，但在 Trippie 必須配合遠端限定才安全——
平台沒有履約證據時，自動確認等於把疑義判給幫手（見上節第 1 點）。
幫手回報完成時**應附上履約紀錄**（訂位編號、交付物、通話結果摘要），
爭議時才有東西可看。

以下兩條仍是**待 Founder 拍板的提案**：

1. **金額不一致** — 標記爭議，整筆排除出統計。對不起來的資料比沒有資料糟。
2. **給一個按下去的理由** — 評價綁在確認之後。確認才能給／收評價，
   讓它對雙方有用，而不是替平台做功德。（自動確認已降低此需求的急迫性，
   但主動確認的資料品質仍高於逾時預設。）

### 檢舉：兩層處置（Founder 核准，2026-09-19）

**立即停權**（先停再查，不等調查完成）：

- 人身安全相關：騷擾、威脅、任何肢體或性方面的指控
- 未到場／未執行卻已收款
- 要求私下轉帳、繞過平台
- 冒用身分、帳號盜用
- 索取超出任務所需的個人資訊（證件、住宿地址）

共通判準：**誤停一個好人的代價，遠低於漏放一個壞人的代價。**

**先審後處理**（不立即停權）：

- 遲到、態度、成果不如預期
- 金額爭議
- 溝通不良

這些是品質問題。直接停權會被拿來打擊競爭對手。

**兩條配套，缺一不可**：

- **立即停權必須有申訴管道**，而且真的有人看。沒有回頭路的系統一定會冤枉人。
- **同一檢舉人反覆檢舉同一對象要能偵測。** 檢舉機制本身會被當成武器。

**檢舉按鈕後面沒有人，比沒有按鈕更糟。** 使用者按了、等了三天沒動靜，
失去的不只是那一次的信任。v1 的檢舉必須做成真的做得到的樣子：

- 被檢舉的交易**立即退出價格統計**（自動，不需要人）
- 標記待人工檢視（v1 的那個人是 Founder）
- 介面**不承諾處理時限**，除非守得住

**檢舉不是負評。** 「他遲到了」是評價；「他沒出現／他要求私下轉帳／他騷擾我」
是檢舉。後果差一個量級，介面與資料都要分開。檢舉涉及對真實的人的指控，
留存期限與可見範圍要另外設計，不可與一般內容同等對待。

### 尚未決定

- **跨國幣別**：幫手在日本收日圓、旅客付台幣，金額以哪一種幣別記錄與比較。
  匯率會變，今天的 5,000 日圓與半年後的 5,000 日圓不是同一個數字——
  平均價要跨時間比較，就得先決定存原幣別還是存當下換算值。**寫 schema 前必須先答。**

- 爭議的實際處理流程（v1 只做標記與停權，不做仲裁）
- **台灣金流相關法規的正式意見——尚未諮詢。** v1 不碰金流所以不急，
  但 v2 押款動工前必須先取得，不可邊做邊問。
